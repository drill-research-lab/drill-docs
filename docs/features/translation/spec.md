# Design: Translation（候選功能）

> 狀態：**待討論，尚未決定是否納入 built-in**。
> 需求來源：[老記(neokent)追加需求原文（2026-08-19）](../../requirements/2026-08-19-neokent-followup.md)。

## 原始需求

> 翻譯頁面：左側 UI 有獨立入口，不需要進聊天。上傳檔案 → 翻譯 → 直接預覽結果 → 可下載。它本質上是 file-in / translated-file-out 的工具。

## 定位

- 獨立於聊天的 **file-in / translated-file-out** 工具
- 使用者上傳檔案、指定翻譯目標、預覽結果後下載
- 翻譯引擎未定；此能力**不必然需要 LLM 或 agent**
- 是否值得成為 Drill built-in 尚未定案，不先建立 translation agent

## 候選使用流程

```text
上傳檔案 → 選擇來源／目標語言 → 翻譯 → 預覽 → 下載翻譯檔
```

最低需求：

1. 不進入聊天即可完成整個流程
2. 顯示處理狀態與翻譯失敗原因
3. 翻譯結果可在 Web UI 預覽
4. 可下載翻譯後的檔案
5. 原始檔與翻譯檔的保存期限、權限與刪除方式必須明確

## 與既有工具的邊界

- 瀏覽器網頁翻譯已有「沉浸式翻譯」等成熟外部工具；Drill 不應重做通用網頁翻譯
- 若只提供一般文字翻譯，獨立 built-in 的價值不足
- 可能形成差異的場景：
  - 翻譯結果直接進入 Drill workspace / 論文庫 / 知識庫
  - 學術術語表、引用、公式與文件結構保留
  - 私有或本地處理，不將研究文件送往第三方服務
  - 批次處理多份研究文件，並保留可追蹤的原文／譯文關係

## UI 位置候選

| 方案 | 說明 | 目前判斷 |
|---|---|---|
| 左側獨立 Translation 頁 | 完整呈現原始需求 | 功能明確，但可能讓側邊欄過度膨脹 |
| Workspace 內的檔案動作 | 選取檔案後執行「翻譯」 | 若 Workspace 成立，較符合工具型能力的定位 |
| 外部工具整合 | 交由既有翻譯服務處理 | 成本最低，但無法形成 Drill 內部 artifact 流程 |

## 非目標

- 不做通用瀏覽器網頁翻譯插件
- 不因為使用模型就建立一個可對話的 translation agent
- 尚未承諾保留所有 PDF / DOCX / PPTX 的原始排版
- 尚未承諾支援即時多人協作翻譯

## 整合點（若納入 built-in）

- **Workspace**：原始檔與翻譯檔作為同一組 artifact 管理
- **Wiki**：翻譯後文件可選擇送入知識庫，但不應自動攝取
- **Paper / Viewer**：沿用文件與 PDF 預覽能力
- **Storage**：沿用 per-user workspace、quota 與 artifact 權限
- **Pipeline**：批次翻譯可成為節點，但不代表一定要有獨立頁面

## 開放問題

1. Built-in 的核心價值是整合 workspace、隱私、本地執行、學術品質，還是只是方便？
2. v1 支援哪些輸入／輸出格式？
3. 是否必須保留原檔格式與排版（例如 DOCX → DOCX、PDF → PDF）？
4. 來源語言是否自動偵測？是否允許一份文件輸出多種語言？
5. 翻譯引擎使用傳統翻譯 API、本地模型、LLM，還是可替換 provider？
6. 是否需要術語表、不可翻譯詞、引用／公式保護與雙語對照？
7. 檔案大小、批次數量、timeout 與失敗重試上限為何？
8. 應有獨立側邊欄入口，還是只作為 Workspace 的檔案動作？

## 納入條件

只有在至少一項 Drill-specific 價值成立時，才升格為正式 built-in：

- 能無縫銜接 workspace / wiki / paper artifact
- 能滿足私有、本地或學術文件品質要求
- 能支援研究工作流中的批次、自動化或可追蹤處理

若以上皆不成立，維持外部工具方案，不進入正式功能列表。
